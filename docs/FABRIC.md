# Microsoft Fabric

How to load this repository into Microsoft Fabric and run it there.

The project lands in a **Fabric Lakehouse**. The Lakehouse is the cloud landing
zone that the rest of the stack reads from: Spark and the SQL endpoint for
data, the semantic model and Power BI for reporting, and the ML prep for the
forecast comparison. Everything Fabric needs is generated by the repo; only the
one-time workspace and capacity steps happen by hand.

## 1. Build the Lakehouse layout

```bash
make fabric-export
```

This writes:

```text
data/export/fabric_lakehouse/
  Tables/            one Parquet folder per warehouse table, ready as shortcut tables
    dim_country/
    dim_region/
    fact_healthcare_workers/
    ...
  Files/             reference material: architecture note, charts, PBIP preview
  _metadata.json     provenance and row counts for the export above
```

Fabric expects Delta tables. Parquetrows ingest cleanly and are converted to
Delta on first write. The `Tables/<name>/<name>.parquet` layout is the
shortcut-ready form.

## 2. Create the workspace and Lakehouse

Scripted, using the Azure CLI against the Fabric REST API:

```bash
# 1. Workspace (skip if you already have one)
az rest --method POST --uri "https://api.fabric.microsoft.com/v1/workspaces" \
  --body '{"displayName":"eu-health-workforce","description":"EU Healthcare Workforce Analytics"}'

# 2. Lakehouse inside that workspace
az rest --method POST \
  --uri "https://api.fabric.microsoft.com/v1/workspaces/<workspaceId>/lakehouses" \
  --body '{"displayName":"health_lakehouse"}'
```

Or by hand: Fabric portal → **Workspaces** → create → **+ Lakehouse** → name it
`health_lakehouse`.

## 3. Upload the tables

### Scripted

```bash
az rest --method POST \
  --uri "https://onelake.blob.fabric.microsoft.com/<workspaceId>/health_lakehouse.Lakehouse/Tables?resource=partition&api-version=2021-12-02" \
  --headers "Content-Type: application/json" --body "{}"
```

The practical equivalent most people use is `azcopy` against the OneLake path
`https://<workspaceId>.onelake.blob.fabric.microsoft.com/<workspaceId>/health_lakehouse.Lakehouse/Tables/`.

### Manual

Open the Lakehouse in the Fabric portal, go to **Get data → Upload**, and drop
the contents of `data/export/fabric_lakehouse/` in.

## 4. Convert Parquet to Delta

Parquet folders are not queryable as tables until they are Delta. Open a notebook
in the Lakehouse and run:

```python
for t in ["dim_country", "dim_region", "fact_healthcare_workers",
          "fact_retirement", "fact_staffing_shortage", "fact_population",
          "fact_population_nuts", "fact_hospital_capacity",
          "fact_regional_workforce", "forecast_workforce"]:
    spark.sql(f"CONVERT TO DELTA lakehouse.Tables.{t}")
```

After this, the Data warehouse model's tables appear under the Lakehouse with
theSQL endpoint automatically.

## 5. Point the Power BI Project at the Lakehouse

The semantic model in `powerbi/pbip/` binds to DuckDB locally. To run it against
Fabric:

1. Publish the Lakehouse tables so the SQL endpoint is available.
2. In Power BI Desktop, open `powerbi/pbip/EU-Health-Workforce.pbip`.
3. Replace the DuckDB M partition source with the Lakehouse SQL endpoint. The
   generic pattern is:

   ```powerquery
   let
       Source = Sql.Database("<workspace>.datawarehouse.windows.net", "<lakehouseName>"),
       Data = Source{[Schema="dbo", Item="<tableName>"]}[Data]
   in
       Data
   ```

4. Refresh, verify a few measures against the preview numbers, then publish to
   the same workspace.

The measure definitions in `powerbi/measures.dax` are engine-agnostic DAX, so
they move over unchanged.

## Why Lakehouse, not a plain warehouse

- The star schema separates dimensions and facts 1:1, which maps directly onto
  the Lakehouse `Tables/` layout.
- Spark and the SQL analytics endpoint read the same Delta tables, so the ML
  prep (`src/ml/forecasting.py`) and the BI report share one source of truth.
- `Files/` holds the architecture note, charts, and the PBIP preview next to
  the data as reference material.

## What Fabric cannot do

- It cannot host `data/healthcare_dw.duckdb` as a live query source. DuckDB is
  a local single-file engine; the Lakehouse replaces it in the cloud.
- It does not run the Python pipeline. `make ingest`, `make warehouse`, and
  `make forecast` still run locally or in CI; Fabric stores their output.

## Tests

`tests/test_fabric.py` verifies the export: every warehouse table exports as
Parquet, row counts match DuckDB, and `_metadata.json` is consistent.
