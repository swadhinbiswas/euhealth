# Deploying to Cloudflare Pages

The `site/` directory is fully static: HTML, one CSS file, one JS file, and a
generated data payload. No build step, no runtime data fetch, no external CDN.
That makes deployment a file copy.

## Recommended: GitHub Pages via Actions (zero configuration)

`.github/workflows/deploy.yml` builds the warehouse, exports the dashboard, and
publishes `site/` to GitHub Pages. Enable it in **Settings → Pages → Source:
GitHub Actions** and push to `main`.

This needs no Cloudflare account and no secrets, and it keeps the site in
version control alongside the code that generated it.

## Cloudflare Pages

**Option A — direct upload (fastest, no CI).**

```bash
# Install once
npm install -g wrangler

# Authenticate
wrangler login

# site/ is the publish root; there is no build command because there is
# nothing to build
wrangler pages deploy site --project-name eu-health-workforce
```

Wrangler prints a `*.pages.dev` URL. Add a custom domain under
**Pages → project → Custom domains**.

**Option B — connect the Git repository.**

Settings → Pages → Create project → Connect to Git, then:

| Setting | Value |
|---|---|
| Framework preset | None |
| Build command | *(leave empty)* |
| Build output directory | `site` |

Since the site is prebuilt, Pages serves `site/` verbatim. If you would rather
regenerate on every push, use the build command from
`Makefile`: `make site`, with output directory `site`.

**Option C — Workers with static assets.**

```bash
wrangler deploy
```

with a minimal `wrangler.toml`:

```toml
name = "eu-health-workforce"
compatibility_date = "2025-01-01"

[assets]
directory = "./site"
```

## After deploying

1. **Verify the numbers against the warehouse.** The site renders whatever was
   in `data/export/site/data.json` at build time. A successful HTTP 200 says
   nothing about whether the data loaded.
2. **Check the caveat block is present.** It is the part of the page that keeps
   the dashboard honest. If a redesign drops it, the site becomes misleading.
3. **Confirm light and dark mode.** The toggle reads `localStorage` and falls
   back to `prefers-color-scheme`.

## Where each artefact belongs

Three deliverables, three different homes. Putting the wrong one in the wrong
place is the usual mistake.

| Artefact | Deploy to | Why |
|---|---|---|
| `site/` — static dashboard + PBIP preview | **Cloudflare Pages** or GitHub Pages | Static HTML, no server. Free, fast, globally cached |
| `powerbi/pbip/` — the Power BI Project | **Power BI Service** (or a repo) | Only Power BI Desktop/Service can execute DAX. Cloudflare cannot host a `.pbix` |
| `data/healthcare_dw.duckdb` | **Object storage** (R2, S3) + refresh job | 9 MB binary; regenerated by the pipeline, never hand-edited |

The important constraint: **Cloudflare Pages cannot run Power BI.** DAX is
evaluated by Power BI's formula engine, not by a browser or a CDN edge worker.
A PBIP is source for Desktop or Service, not a web page. Publishing it to Pages
would serve JSON files that nothing executes.

So the sensible split is a GitHub Pages or Cloudflare Pages site for the
readable dashboard, plus the PBIP in version control where a reviewer opens it
in Desktop, and optionally a Power BI Service workspace for the published
report.

## Publishing the report to Power BI Service

Once Desktop has opened the PBIP and refreshed it:

```bash
# Publish from Desktop: File → Publish to Power BI Service
```

Or from the CLI with `pbi-tools`, using a deployment pipeline:

```bash
# pbi-tools deploy ./powerbi/pbip <workspace> Production
```

The PBIP format was chosen partly for this: because the report is diffable
text, a deployment pipeline can promote a specific environment to production
from a tagged build, which a `.pbix` binary makes awkward.

### Publishing to Fabric or the Power BI REST API

For CI-driven publication, use a Power BI pipeline:

1. **Workspace → Pipelines** in the Power BI Service admin portal.
2. Create a pipeline with `development`, `test`, `production` stages.
3. Store the connection strings as repository secrets.
4. Trigger the pipeline on tag, via the Power BI REST API.

```yaml
- name: Deploy to Power BI
  env:
    AZURE_CLIENT_ID: ${{ secrets.PBI_CLIENT_ID }}
    AZURE_TENANT_ID: ${{ secrets.PBI_TENANT_ID }}
    AZURE_CLIENT_SECRET: ${{ secrets.PBI_CLIENT_SECRET }}
  run: |
    TOKEN=$(curl -s -X POST "https://login.microsoftonline.com/$AZURE_TENANT_ID/oauth2/v2.0/token" \
      -d "grant_type=client_credentials&client_id=$AZURE_CLIENT_ID\
&client_secret=$AZURE_CLIENT_SECRET&scope=https://analysis.windows.net/powerbi/api/.default" \
      | jq -r .access_token)
    curl -s -X POST "https://api.powerbi.com/v1.0/myorg/pipelines/$PIPELINE_ID/run" \
      -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
      -d "{\"stage\":2}"
```

The service principal needs the **Power BI Contributor** workspace role. Do not
put the token in a build log — pipe it to a variable and never echo it.

## Publishing the DuckDB warehouse

The warehouse is 9 MB, which is too large to commit and pointless to serve
statically. It belongs in object storage with a scheduled refresh:

```bash
# R2 via wrangler
wrangler r2 object put healthcare/healthcare_dw.duckdb --file=data/healthcare_dw.duckdb
```

Then the PBIP's DuckDB M query can point at a presigned URL, or the pipeline
can regenerate the PBIP's Parquet snapshots from the refreshed warehouse and
re-publish the report.

## A note on data freshness

The deployed site is a **snapshot** generated at build time. It states its
vintage on the page. If you need a live dashboard instead of a portfolio
artefact, the honest options are a scheduled build (daily Actions run) or a
Pages Function reading the warehouse — at the cost of moving credentials into
production.

## Why static

A dynamic dashboard would need a server, a database connection and a runtime
data source — which means credentials in production and a page that breaks when
Eurostat is unreachable. Generating the payload at build time means the deployed
site is a snapshot with a stated vintage, served from a CDN, and costs nothing
to host.

The trade-off is real: a deployed snapshot goes stale until the next build. For
a portfolio artefact that is the right trade; for an operational tool, wire up
Pages Functions against the warehouse instead and move the export step to a
scheduled build.
